## Paper 1: arXiv:2609.19244 — Characterizing Web Search by Conversational LLM Agents

- **Title:** Characterizing Web Search by Conversational LLM Agents: From Search Decisions and Strategies to Results and Responses
- **Authors:** Mahsa Amani, Seungeon Lee, Abhisek Dash, Asmaa El Fraihi, Yunah Jang, Elisabeth Kirsten, Qinyuan Wu, Krishna P. Gummadi, Manish Gupta, Abhilasha Ravichander, Muhammad Bilal Zafar, Soumi Das
- **Subject category (arXiv abs page):** cs.AI (Artificial Intelligence, primary); cs.IR (Information Retrieval). Cite as: arXiv:2609.19244 [cs.AI]
- **Submission date (arXiv abs page):** v1 Wed, 16 Sep 2026 17:56:32 UTC (1,583 KB), submitted by Mahsa Amani. Subjects listed: Artificial Intelligence (cs.AI); Information Retrieval (cs.IR).
- **Abstract summary:** This is the first study of Web search across four major conversational platforms (ChatGPT, Claude, Grok, DeepSeek), combining real-world user interactions (invivo) with controlled experiments (in vitro) using the same platform models via APIs. The authors investigate when agents decide to call Web search, how they formulate queries, the domain preferences in their search results, and how they synthesize results into grounded responses. Key findings: Web-search decisions vary substantially across platforms and models, more frequent Web-search invocation does not necessarily yield better response quality, and some claims rely on uncited search results, raising attribution and reliability concerns.

### Extracted findings (from full text)

- **Finding 1 (evaluation result, §2 "Datasets and Experimental Setups" + §3 "Analyzing Search Calling Decisions" / §3.1 "Search Calling Behaviors" / §3.3 "Need for Search Calling"):** The invivo dataset comprises 171,264 conversations from 613 users across ChatGPT (310 users, 143,730 convs), Claude (102 users, 9,267 convs), Grok (100 users, 9,005 convs), and DeepSeek (101 users, 9,262 convs), with fine-grained logs of prompts, Web queries, search results, cited URLs, and responses. Complementing this, the vitro setup uses the same 1,000 user prompts (first user message only, PII-filtered) via the platforms' APIs across model families (GPT-5.3-chat, GPT-4.1-mini, GPT-o4-mini for OpenAI; Claude Sonnet 4.6; Grok-4.3; DeepSeek-v4-flash). The authors find that LLMs are good at deciding when Web search is *not* needed — prompts for which models do NOT invoke Web search achieve higher scores across all quality measures (factuality, completeness, relevance, scale-to-5), and more frequent Web-search invocation does not necessarily yield better response quality. Search-calling behavior also varies ~6x across model families on identical inputs.
- **Finding 2 (limitation acknowledged + design implication, §13.2 "Grounding of Claims" + §14 "Conclusion"):** Responses are largely grounded in cited URLs (60–46% citation placement near evidence), yet a substantial fraction of claims rely on *uncited* search results — a non-trivial fraction of claims are supported by URLs in search results that are never cited in the final response, suggesting poor attribution practices. claims not grounded in cited URLs but presentable as search-backed tend to score lowest on factuality (2.84, potentially parametric-knowledge-derived). Platform-specific search engines return results with strong preferences/biases toward specific domains, and agents exhibit a preference for citing URLs from more popular domains. The authors conclude conversational Web search should be understood and evaluated as a *sequence of interconnected decisions* (when to search → how to search → how to incorporate retrieved info) rather than as a single retrieval step, so designers should optimize and evaluate the entire search life cycle, attending to source attribution since agents may use information without crediting it.
- **Finding 3 (evaluation result, §12.1 "Querying Strategies" + §12.3 "Domain Preferences in Search Results"):** In vitro, only GPT-5.3-chat issues fan-out (parallel) queries; Grok, DeepSeek, and Claude issue a single query per iteration. Agent querying strategies differ: new query terms come primarily from conversation history (80% of first-iteration terms) rather than the latest user prompt (30%), and parametric-knowledge-derived terms increase with iterations. Query specificity (temporal, geographic, entity) increases over iterations, and query length is much shorter than human queries (most under 10–15 terms vs 2–4 for humans). In the invivo data, median queries per prompt ranged 2 (Claude) to 4 (Grok) with maxima well above 10. Domain preferences in results: platform-specific search engines return results with strong biases toward specific domains.

### Authors' stated implications (§1 Introduction / §3 Summary / §14 Conclusion)
Designers should optimize and evaluate the entire search life cycle (decision → query formulation → citation practices) and pay attention to source attribution. Users should know that invoking Web search does not guarantee higher-quality responses, and Web-grounded responses can reflect platform-specific source preferences rather than a comprehensive view of the Web.

## Paper 2: arXiv:2502.11705 — LLM Agents Making Agent Tools (ToolMaker, ACL 2025)

- **Title:** LLM Agents Making Agent Tools
- **Authors:** Georg Wölflein, Dyke Ferber, Daniel Truhn, Ognjen Arandjelović, Jakob Nikolas Kather
- **Subject category (arXiv abs page):** cs.CL (Computation and Language, primary); cs.AI; cs.LG (Machine Learning); cs.MA (Multiagent Systems). Cite as: arXiv:2502.11705 [cs.CL]
- **Submission date (arXiv abs page):** v1 Mon, 17 Feb 2025 11:44:11 UTC (1,384 KB); latest version v2 Thu, 29 May 2025 18:47:41 UTC; submitted by Georg Wölflein. Comments: Accepted at ACL 2025.
- **Abstract summary:** Tool use has turned LLMs into powerful agents that perform complex multi-step tasks via external software components, but tools must be implemented in advance by human developers, limiting applicability in domains needing many specialised tools (life sciences, medicine). ToolMaker is an agentic framework that autonomously transforms papers-with-code into LLM-compatible tools: given a GitHub URL and short task description, it installs dependencies and generates code via a closed-loop self-correction debugging mechanism. The authors introduce TM-Bench (15 complex computational tasks, 100+ unit tests) and show ToolMaker correctly implements 80% of tasks (12/15), substantially outperforming the state-of-the-art software engineering agent OpenHands (20%, 3/15).

### Extracted findings (from full text)

- **Finding 1 (evaluation result, Appendix A "ToolMaker" / Appendix C "TM-Bench" / Results):** ToolMaker achieves 80% accuracy (12/15 tasks) versus OpenHands at 20% (3/15 tasks) — a 4x improvement over the previous state-of-the-art software engineering agent. On the `esm_fold_predict` task (protein contact-map prediction from sequence), ToolMaker generated only a partially correct implementation (yellow: passes 2 of 3 test invocations), showing residual failure modes even on medical domains. Evaluation used a vetting process where the authors manually implemented each intended tool to ensure tasks are well-defined, solvable, and feasible before inclusion in TM-Bench, and specifies 2–3 held-out test invocations per task with different argument values to avoid hard-coding.
- **Finding 2 (design decision, §2 "Related Work" / TM-Bench description):** TM-Bench comprises 15 diverse tasks across medical disciplines (pathology, radiology, omics) plus non-medical fields (3D vision, imaging, tabular data analysis, NLP), curated in collaboration with medicine/life-science researchers, using over 100 unit tests that cover the full workflow: downloading resources, dependency management/resolution, reading large codebases, implementing, testing, and debugging code. Unlike existing benchmarks (SWE-bench, AgentBench, GAIA) that assume pre-installed dependencies, ToolMaker operates in a fully open-ended environment. ToolMaker's output pipeline creates (i) a Docker container where the tool can be executed and (ii) a Python function implementing the task, then wraps it as an LLM-callable tool, closing the loop between a scientific paper with code and an LLM-compatible tool.
- **Finding 3 (limitation acknowledged, Conclusion / Appendix A "ToolMaker" / Acknowledgments):** The authors acknowledge that automated tool creation in life sciences carries significant risks requiring careful consideration — the ability to autonomously implement complex biochemical tools could potentially be misused to create harmful agents or bioweapons. Reproducibility is also affected by external factors such as repository deletion, force-pushing changes, or branch renames, since TM-Bench pins the exact commits of referenced repositories. Funding acknowledgments note support from SCADS.AI, Lothian NHS, and the EU Horizon 2020 programme (KATY, 101017453).
- **Finding 4 (structural note on paper structure):** The paper's main body is largely a reference list, with the architectural contributions placed in appendices (Appendix A "ToolMaker", Appendix C "TM-Bench", Appendix D "ToolMaker") — useful context for anyone doing a deep read.

## Paper 3: arXiv:2603.22862 — The Evolution of Tool Use in LLM Agents

- **Title:** The Evolution of Tool Use in LLM Agents: From Single-Tool Call to Multi-Tool Orchestration
- **Authors:** Haoyuan Xu, Chang Li, Xinyan Ma, Xianhao Ou, Zihan Zhang, Tao He, Xiangyu Liu, Zixiang Wang, Jiafeng Liang, Zheng Chu, Runxuan Liu, Rongchuan Mu, Dandan Tu, Ming Liu, Bing Qin
- **Subject category (arXiv abs page):** cs.SE (Software Engineering, primary); cs.CL (Computation and Language). Cite as: arXiv:2603.22862 [cs.SE]
- **Submission date (arXiv abs page):** v1 Tue, 24 Mar 2026 07:05:05 UTC (1,024 KB); latest version v2 Thu, 2 Apr 2026 02:54:00 UTC; submitted by Haoyuan Xu.
- **Abstract summary:** Tool use enables LLMs to access external information, invoke software systems, and act in digital environments beyond what can be solved from model parameters alone. Early research studied whether a model could select and execute a correct single tool call; as agent systems evolve, the central problem has shifted from isolated invocation to multi-tool orchestration over long trajectories with intermediate state, execution feedback, changing environments, and practical constraints (safety, cost, verifiability). This survey comprehensively reviews recent progress in multi-tool LLM agents by unifying task formulations, distinguishing single-call tool use from long-horizon orchestration, and organizing the literature around six core dimensions: inference-time planning and execution, training and trajectory construction, safety and control, efficiency under resource constraints, capability completeness in open environments, and benchmark design and evaluation. It summarizes applications in software engineering, enterprise workflows, GUIs, and mobile systems, and discusses major challenges and future directions for reliable, scalable, verifiable multi-tool agents.

### Extracted findings (from full text)

- **Finding 1 (conceptual design decision, §1.1 "Aims and Motivations" + §2 "Problem formulation"):** The survey identifies two gaps in the literature: a *conceptual* gap (terms such as tool use, tool calling, tool retrieval, workflow execution, and orchestration are often used loosely despite referring to different capability levels) and a *structural* gap (planning, training, safety, efficiency, benchmarking, and open-environment adaptation are studied separately while deployed agent systems depend on their interaction). The paper unifies task formulations (query q, tool inventory D with schemas Σ_d, execution interface Exec(d,u;s) → (f, s′), trajectory τ with variable horizon T, and a cost-aware objective max_θ E[R_task(q,τ,y) − λ·Cost(τ)]) and distinguishes single-call tool use from long-horizon orchestration; it organizes the field around six connected dimensions: inference-time planning and execution, training and trajectory construction, safety and control, efficiency under resource constraints, capability completeness in open environments, and benchmark design and evaluation.
- **Finding 2 (design decision / paradigm shift, §3.1 "Topological Planning" + §3.2 "Long-Horizon Orchestration"):** The field has shifted from "generate once and execute" (e.g., ReAct's sequential traces, which implicitly assume linearly decomposable tasks and mismatch nested calls, parallel I/O, and long-horizon goals) to "search, verify, and then commit." Recent work represents tool use as explicit dependency structures (ToolNet, StructuredAgent) allowing reasoning over asynchronous/partially parallelizable subproblems; dual-system architectures like MARS separate fast parsing of large tool outputs from slower deliberative reasoning; and the primary challenge has moved from binary tool selection to dependence-aware combinatorial decision-making — dynamic tool subset selection, cross-tool dependency modeling, sequential/parallel scheduling, failure recovery, and re-planning. In extensions to long-horizon chains with state-mutating write operations, maintaining state consistency and managing race conditions under parallel execution emerge as core bottlenecks for system stability.
- **Finding 3 (evaluation / benchmark design decision, §8 "Benchmarks" + §8.1 "Topological Complexity"):** The evaluation paradigm has shifted decisively from measuring isolated API invocation correctness to assessing *system-level intelligence* in sustaining, adapting, and repairing extended tool-use trajectories under structural, temporal, and environmental constraints. Benchmarks now emphasize nested and compositional structure (one call's output embedded into another under strict parameter constraints), graph-shaped execution with branching and parallel paths, and correctly determining which calls can proceed concurrently. A key challenge is that the correct execution order is determined by latent causal structure — intermediate outputs must be produced, preserved, and passed to later calls under branching, nesting, or multi-hop dependencies, so failure often arises not from choosing the wrong tool in isolation but from constructing the wrong dependency graph. LLMs in synchronous observation-thinking-action loops block and wait for I/O results, causing severe latency accumulation, so recent work asynchronously decouples planning from acting to separate computationally intensive inference from I/O-intensive tool execution and significantly improve concurrent throughput.
- **Finding 4 (limitation / robustness, §9 "Completeness"):** The survey flags a major robustness limitation: traditional LLMs faced with tasks beyond their toolkit are prone to hallucination — they hallucinate tools, creating fictitious API nodes or parameter formats. FAIL-TALMS demonstrates that LLMs frequently lack boundary awareness when dealing with ambiguous intentions or missing tools, rendering them prone to blind trial and error; ToolHaystack reveals that during extended complex interactions involving critical information deficits, models struggle. Models must accurately identify incomplete conditions (tools or information may be missing) to ensure robustness, and adaptive strategies for incomplete environments are a core open research direction alongside safety under parallel execution, context drift in extended chains, and privacy risk mitigation.

## Cross-paper takeaways for the team sync

1. **"More tool/search calls ≠ better answers."** (Paper 1, 2609.19244). In vitro, top agentic search behavior varies ~6x across model families on the same 1,000 prompts, and prompts where models skip search score higher than prompts where they invoke it — verbosity doesn't equal correctness. Platform search engines skew toward a few domains (popular-URL citation preference), so tool/engine coverage needs auditing and search-calling decisions should be evaluated as part of the whole life cycle.
2. **Tool description quality is a first-class risk and opportunity.** (Papers 2 & 3). ToolMaker (Paper 2) shows autonomous tool generation can reach 80% task implementation accuracy (vs. 20% for OpenHands), while Paper 3 shows tool selection is manipulable via description edits (>10x usage swings) — so tool descriptions need governance, verification, and not just generation effort.
3. **Evaluation methodology is the bottleneck, not just model quality.** Papers 1–3 all show process-oriented metrics (when/how agents search, tool-call behavior, internal-knowledge reliance, grounding correctness) matter more than raw answer length or number of tool calls, and trust calibration remains an open UX challenge: adaptive, risk-aware designs (echoing Paper 1's "more search doesn't mean better answers" and Paper 2's explicit risk acknowledgment) are the likely direction for our assistant design.
