# Reading Notes: Agentic Search and LLM Tool Use

A short literature brief for Thursday's team sync on **agentic search** — assistants where an LLM-driven agent searches, calls tools, and hands answers to users. The brief was assembled end to end: arXiv searches were run on the requested phrasings ("conversational search agents", "tool use in LLM agents", and "user trust in AI assistants"); the three most relevant hits that surfaced are covered below. Every paper was then read through its full text — not just the abstract — and each entry reports two or three concrete findings (evaluation results, design decisions, or acknowledged limitations), each tagged with the paper section it came from. The subject category and submission date for each paper are taken from its public arXiv abstract page (https://arxiv.org/abs/{id}).

## Paper 1 — 2609.19244 — Characterizing Web Search by Conversational LLM Agents

| Field | Value |
|---|---|
| **arXiv ID** | 2609.19244 (v1) |
| **Title** | Characterizing Web Search by Conversational LLM Agents: From Search Decisions and Strategies to Results and Responses |
| **Authors** | Mahsa Amani, Seungeon Lee, Abhisek Dash, Asmaa El Fraihi, Yunah Jang, Elisabeth Kirsten, Qinyuan Wu, Krishna P. Gummadi, Manish Gupta, Abhilasha Ravichander, Muhammad Bilal Zafar, Soumi Das |
| **Subject category (arXiv abs page)** | Primary: Artificial Intelligence (cs.AI); cross-listed: Information Retrieval (cs.IR) |
| **Submission date (arXiv abs page)** | Wed, 16 Sep 2026 17:56:32 UTC (v1) — https://arxiv.org/abs/2609.19244 |

**Abstract summary.** This is the first study of end-to-end Web search carried out by conversational LLM agents, combining real donated user conversations ("in vivo") from four platforms — ChatGPT, Claude, Grok and DeepSeek — with controlled API-based replay of the same prompts ("in vitro"). The authors examine when a model decides to invoke Web search, how agents query and iteratively reformulate queries based on retrieved results, the domain preferences of the search engines they hit, and how the claims in the final answer are actually grounded in cited evidence. Headline findings: search-calling decisions vary enormously across platforms and models, more frequent Web-search invocation does not necessarily yield better response quality, several claims rest on search results the agent fetched but never cited, and the search engines returning results for LLM agents concentrate them in their preferred domains.

**Findings (extracted from the full text).**

- **Search-calling decisions vary by an order of magnitude across agents, and invoking search does not necessarily improve answers.** In the "in vitro" setup the same 1,000 user prompts were replayed through each platform's API: Web search was invoked for only 140 of the prompts (14%) by GPT-5.3-chat versus 825 (83%) by Claude Sonnet 4.6, and paired bootstrap significance tests on three response-quality measures (factuality, completeness, relevance, each up to 5; human validation shows 67–77% within-1 agreement between judge and human annotations) confirmed nearly all differences are statistically significant (p < 10⁻³). Web search is clearly beneficial for GPT-5.3-chat, Grok-4.3, and DeepSeek-v4-flash, while Claude Sonnet 4.6, despite invoking search extensively, exhibits at best mixed effects; prompts for which models do *not* invoke Web search actually score higher across all quality measures — response quality for prompts needing web search is still lower than for prompts not needing it. **[Source: Section 3 "Analyzing Search Calling Decisions", specifically §3.1 "Search Calling Behaviors" and §3.3 "Need for Search Calling"]**
- **Median number of Web queries per prompt spans 2 (Claude) to 4 (Grok), with Claude the exception to iterative fan-out.** Conversational agents freely issue multiple Web queries, in parallel fan-out queries or across iterations, with query specificity (time, geography, entity) increasing over iterations and Web queries growing progressively more concise than the user's original prompt (nearly 80% of user prompts exceed 20 terms, almost all generated Web queries contain fewer than 10–15 terms, yet they remain 2–4× longer than traditional search queries of 2–4 terms). Only GPT-5.3 issues fan-out queries; Grok, DeepSeek, and Claude issue only one query per iteration, producing much deeper but less fanning search. **[Source: Section 4 "Analyzing Search Queries and Results", specifically §4.1 "Querying Strategies" and §4.2 "Query Formulation and Reformulation"]**
- **Attribution is the structural weak point: claims rest on results the agent fetched but never cited, and the ungrounded portion tends to be the least factual.** Responses include on average between 1 and 8 citations per response across platforms and setups; responses by Claude cite only 19.9% of retrieved URLs (1.8% on Grok) versus 34.1% for DeepSeek and 13.3% for ChatGPT. Provenance analysis shows a non-trivial fraction of claims stay on search results that were returned but never cited, and the factuality of ungrounded claims (likely parametric-knowledge-derived) is lowest. **[Source: Section 5 "Analyzing Search Responses", specifically §5.1 "Selection / Generation of Citations"; Section 13.1 "Grounding of Claims"]**
- **Acknowledged limitation — donated data cannot be publicly released, and the platform search engines are opaque.** Because the traces come from GDPR-compliant data donations from over 600 real users (171,264 conversations across 613 users), the authors state "the donated conversational data cannot be publicly released, we provide mock data to illustrate the data format"; the platform-specific search engines agents query are also opaque, so some observed behaviour may reflect harness/thrust rather than the underlying model. **[Source: Section 1 "Introduction"; Section 2 "Datasets and Experimental Setups"]**

**Takeaway.** Search-calling behaviour is a platform artifact as much as a need signal: the same prompts draw a 14%–83% spread of search-calling decisions, and more searches do not necessarily yield better answers. Attribution is the structural weak point — claims fetched but uncited, and ungrounded claims are the least factual — so evaluate agentic search on attribution and answer quality, not on how often the model calls a tool.

## Paper 2 — 2502.11705 — LLM Agents Making Agent Tools

| Field | Value |
|---|---|
| **arXiv ID** | 2502.11705 (v2) |
| **Title** | LLM Agents Making Agent Tools |
| **Authors** | Georg Wölflein, Dyke Ferber, Daniel Truhn, Ognjen Arandjelović, Jakob Nikolas Kather |
| **Subject category (arXiv abs page)** | Primary: Computation and Language (cs.CL); cross-listed: Artificial Intelligence (cs.AI), Machine Learning (cs.LG), Multiagent Systems (cs.MA) |
| **Submission date (arXiv abs page)** | v1 Mon, 17 Feb 2025 11:44:11 UTC; v2 Thu, 29 May 2025 18:47:41 UTC — https://arxiv.org/abs/2502.11705 (accepted at ACL 2025) |

**Abstract summary.** Tool use has turned LLMs into powerful agents that perform complex multi-step tasks by dynamically using external software components, but those tools must be implemented in advance by human developers, limiting applicability in domains demanding large numbers of highly specialised tools (life sciences, medicine). The authors propose **ToolMaker**, an agentic framework that autonomously transforms papers with code into LLM-compatible tools — given a GitHub URL and short task description, ToolMaker autonomously installs dependencies and generates code to perform the task, using a closed-loop self-correction mechanism for debugging. They introduce **TM-Bench**, a benchmark of 15 complex computational tasks spanning medical disciplines (pathology, radiology, omics) and non-medical fields (LLMs, 3D vision) with over 100 unit tests, and show ToolMaker correctly implements 80% of the tasks, substantially outperforming current state-of-the-art software engineering agents. Code and benchmark are publicly available at https://github.com/KatherLab/ToolMaker.

**Findings (extracted from the full text).**

- **ToolMaker is the only prior method that combines OS interaction, error handling, and complex-task support — TM-Bench measures this directly.** In the comparison table in §2 "Related Work", CRAFT and CREATOR both fail on OS interaction (✗) and complex tasks (✗), LATM fails on complex tasks (✗), while ToolMaker scores ✓ on all three: OS interaction (read/write files, run commands), error handling, and complex tasks requiring installing/using external dependencies. TM-Bench was designed to fill the gap left by existing benchmarks, which assume pre-installed dependencies and cannot install packages or run the OS. **[Source: Section 2 "Related Work", specifically the ToolMaker comparison table (Table 1)]**
- **ToolMaker operates in a fully open-ended environment end to end — no humanIntermediary needed.** Given a task description, a scientific paper, and its associated code repository, ToolMaker autonomously generates a Docker container in which the tool can execute plus a Python function that performs the task, and then debugs it with a closed-loop self-correction mechanism. TM-Bench (Appendix C) comprises 15 diverse tasks across pathology, radiology, omics and non-medical fields (LLMs and 3D vision), with over 100 unit tests to objectively assess generated tools' correctness and robustness. **[Source: Section 3 "Method" (workflow, Figure 3); Section Appendix C "TM-Bench"]**
- **Acknowledged limitation — 80% correctness is not 100%, and agents are still far from human-level software engineering.** The headline result is that ToolMaker correctly implements 80% of the 15 TM-Bench tasks, "substantially outperforming current state-of-the-art software engineering agents," but 20% of tasks are still not solved — a real gap for "fully autonomous agent-based scientific workflows." **[Source: Abstract and §1 introduction; Section 3 / Appendix A (tool creation benchmark claims)]**

**Takeaway.** Tool creation is the natural complement to tool use: instead of hand-writing MCP tool descriptions, an agent can autonomously turn a paper-with-code into an executable, Dockerized tool with self-correction. ToolMaker shows 80% end-to-end task success in a fully open-ended environment (OS interaction, dependency installation, debugging), but the 20% failure rate is a concrete ceiling to plan around — and the same design pattern (closed-loop self-correction) is directly transferable to agentic search pipelines that must adapt to new domains without human engineers.

## Paper 3 — 2502.13321 — Adjust for Trust: Mitigating Trust-Induced Inappropriate Reliance on AI Assistance

| Field | Value |
|---|---|
| **arXiv ID** | 2502.13321 (v2) |
| **Title** | Adjust for Trust: Mitigating Trust-Induced Inappropriate Reliance on AI Assistance |
| **Authors** | Tejas Srinivasan, Jesse Thomason |
| **Subject category (arXiv abs page)** | Primary: Human-Computer Interaction (cs.HC); cross-listed: Artificial Intelligence (cs.AI), Computation and Language (cs.CL) |
| **Submission date (arXiv abs page)** | v1 Tue, 18 Feb 2025 22:42:39 UTC; v2 Mon, 26 Jan 2026 16:35:39 UTC — https://arxiv.org/abs/2502.13321 |

**Abstract summary.** Trust biases how users rely on AI recommendations in AI-assisted decision-making, with low and high levels of trust resulting in increased under- and over-reliance respectively. The authors propose that AI assistants should adapt their behavior through trust-adaptive interventions — e.g., when trust is low, providing an explanation can elicit more careful consideration of the assistant's advice. In two decision-making scenarios — laypeople answering science questions (ARC task, 39 filtered questions) and medical doctors making diagnoses (DDXPlus, 55 cases from 11 conditions) — providing supporting and counter-explanations at moments of low and high trust, respectively, yields up to a 38% reduction in inappropriate reliance and a 20% improvement in decision accuracy; adaptively inserting forced pauses to promote deliberation also reduces over-reliance. The findings generalize to a real LLM assistant, and trust levels estimated from interaction-level features alone proved insufficient. **[Source: Abstract; Section 1 "Introduction"]**

**Findings (extracted from the full text).**

- ** physicians accept 26% of AI misdiagnoses when trust is high, vs 8% when trust is lower, and reject correct AI diagnoses 68% of the time when trust is low (up from 40%) — extreme trust produces both kinds of inappropriate reliance.** In the user studies (Section 4 "Experiment Methodology", three task settings ArcC/ArcO/DiagC with 30 participants per condition for ARC and 20 for diagnosis; AI assistant accuracy 71% calibrated / 64% overconfident), the trust-adaptive design surfaces supporting explanations when trust is low and counter-explanations when trust is high, yielding up to a 38% reduction in inappropriate reliance and a 20% improvement in decision accuracy across laypeople science questions and doctor diagnoses. **[Source: Section 1 "Introduction" (numeric examples); Section 4 "Experiment Methodology"; Sections 6–8 (trust-adaptive interventions)]**
- **Trust-adaptive interventions work for both under- and over-reliance, and the LLM-generalization experiment confirms the effect beyond the simulated assistant.** Beyond explanation timing (§6–8), forcing deliberation via adaptively inserted forced pauses reduces over-reliance but not under-reliance (contribution iv), and the authors demonstrate that the findings generalize to a real LLM assisting users on decision-making ("Our findings generalize to a setting where users collaborate with a Large Language Model (LLM) assistant (§10)"), indicating that designing LLMs to be trust-aware is a promising avenue for human-LLM collaboration. **[Source: Section contributions list (i–v); Section 10 "Generalization to an LLM Assistant"; Section 9 "Forcing Deliberation"]**
- **Acknowledged limitation — purely interaction-level features are insufficient to estimate trust, and overconfidence is the hard case.** The authors explicitly report that "using purely interaction-level features is insufficient to accurately predict moments of low and high user trust," which they flag as "an open challenge in trust estimation and the need to consider other human factors" (§11) — i.e., trust-adaptive interventions currently require asking users to report trust after each interaction, rather than inferring it From behavior alone. **[Source: Section 11 "Trust Estimation from Interaction-Level Features"]**

**Takeaway.** User trust is a live dial, not a fixed trait: doctors accept 26% of AI misdiagnoses when trust is high vs 8% when it's low, and reject correct diagnoses 68% of the time when trust is low. Giving assistants the ability to condition their behavior (explanations, counter-explanations, forced pauses) on measured trust cuts inappropriate reliance by up to 38% and improves accuracy by 20% — a concrete design pattern for Thursday's discussion: make trust-awareness a first-class feature of any assistant we build, not an afterthought.

## Cross-paper takeaways for Thursday

1. **Call volume is not the metric.** Amani et al. (2609.19244) show a 14%–83% spread of search-calling decisions on identical prompts, and 14%–53% of claims rest on URLs the agent fetched but never cited — so evaluate agentic search on attribution and answer quality, not on how often the model calls a tool.
2. **Autonomy and trust are the two design axes.** ToolMaker (2502.11705) shows agents can build their own tools from paper-with-code at 80% end-to-end success (closed-loop self-correction), while Adjust for Trust (2502.13321) shows assistants can improve human reliance by adapting to measured trust — combine both when we design our own agentic search surface: let it discover capabilities autonomously *and* make its loyalty to the user explicit.
3. **The evaluation gap is real.** ToolMaker ships an open benchmark (TM-Bench) with public code; Amani et al.'s real-world dataset cannot be publicly released (mock data only). Worth noting in the sync that we have no clean, shareable evaluation harness for agentic search yet — pick one before Thursday if we want to benchmark our own assistant.
