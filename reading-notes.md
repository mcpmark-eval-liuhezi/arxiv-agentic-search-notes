# Reading Notes: Agentic Search and LLM Tool Use

A short literature brief for Thursday's team sync on **agentic search** — assistants where an LLM-driven agent searches, calls tools, and hands answers to users. The brief was assembled end to end: arXiv searches were run on the requested phrasings ("conversational search agents", "tool use in LLM agents", and "user trust in AI assistants"), and the three most relevant hits that surfaced are covered below. Every paper was then read through its full text, not just the abstract, and each entry reports two or three concrete findings (evaluation results, design decisions, or acknowledged limitations), each tagged with the paper section it came from. Subject category and submission date are taken from each paper's public arXiv abstract page. Findings in this file are quoted or paraphrased from the full manuscripts.

## Paper 1 — 2609.19244 — Characterizing Web Search by Conversational LLM Agents

| Field | Value |
|---|---|
| **arXiv ID** | 2609.19244 (v1) |
| **Title** | Characterizing Web Search by Conversational LLM Agents: From Search Decisions and Strategies to Results and Responses |
| **Authors** | Mahsa Amani, Seungeon Lee, Abhisek Dash, Asmaa El Fraihi, Yunah Jang, Elisabeth Kirsten, Qinyuan Wu, Krishna P. Gummadi, Manish Gupta, Abhilasha Ravichander, Muhammad Bilal Zafar, Soumi Das |
| **Subject category (arXiv abs page)** | Primary: Artificial Intelligence (cs.AI); cross-listed: Information Retrieval (cs.IR) |
| **Submission date (arXiv abs page)** | Wed, 16 Sep 2026 17:56:32 UTC (v1) — https://arxiv.org/abs/2609.19244 |

**Abstract summary.** This is the first study of end-to-end Web search carried out by conversational LLM agents, combining real donated user conversations ("in vivo") from four platforms — ChatGPT, Claude, Grok and DeepSeek — with controlled API-based replay of the same prompts ("in vitro"). The authors examine when a model decides to invoke Web search, how agents query and iteratively reformulate queries based on retrieved results, the domain preferences of the search engines they hit, and how the claims in the final answer are actually grounded in cited evidence. Headline findings: search-calling decisions vary enormously across platforms and models, more frequent Web-search invocation does not necessarily yield better response quality, several claims rest on search results the agent fetched but never cited, and the search engines returning results for LLM agents concentrate them in their preferred domains.

**Findings (extracted from the full text).**

- **Search-calling decisions vary by an order of magnitude across agents, and invoking search does not necessarily improve answers.** In the "in vitro" setup the same 1,000 user prompts were replayed through each platform's API: Web search was invoked for only 140 of the prompts (14%) by GPT-5.3-chat versus 825 (83%) by Claude Sonnet 4.6, and paired bootstrap significance tests on three response-quality measures (factuality, completeness, relevance, each up to 5) confirmed nearly all differences are statistically significant (p < 10^-3). Web search is clearly beneficial for GPT-5.3-chat, Grok-4.3, and DeepSeek-v4-flash, while Claude Sonnet 4.6, despite invoking search extensively, exhibits at best mixed effects; what is more, prompts for which models do *not* invoke Web search score higher across all quality measures — response quality for prompts needing web search is still lower than for prompts not needing it. **[Source: Section 3 "Analyzing Search Calling Decisions", specifically §3.1 "Search Calling Behaviors" and §3.3 "Need for Search Calling"]**
- **Median number of Web queries per prompt spans 2 (Claude) to 4 (Grok), with median maximum well above 10; Claude is the exception to iterative fan-out.** Conversational agents freely issue multiple Web queries, in parallel fan-out queries or across iterations, with query specificity (time, geography, entity) increasing over iterations and Web queries growing progressively more concise than the user's original prompt (nearly 80% of user prompts exceed 20 terms, almost all generated Web queries contain fewer than 10–15 terms, yet they remain 2–4x longer than traditional search queries of 2–4 terms). Only GPT-5.3 issues fan-out queries; Grok, DeepSeek, and Claude issue only one query per iteration, producing much deeper but less fanning search. **[Source: Section 4 "Analyzing Search Queries and Results", specifically §4.1 "Querying Strategies" and §4.2 "Query Formulation and Reformulation"]**
- **Attribution is the structural weak point: a large share of claims rest on results the agent never cited, and the ungrounded portion tends to be the least factual.** Search engines on Claude and Grok return roughly 10 results per query, DeepSeek roughly 5, and ChatGPT roughly 15 — far fewer than a typical Google search — and provenance analysis shows 14% to 53% of all claims sit on search results that were returned but never cited in the response, with factuality highest for claims grounded in associated citations and lowest for ungrounded claims (likely parametric-knowledge-derived). **[Source: Section 4 "Analyzing Search Queries and Results", specifically §4.3 "Domain Preferences in Search Results"; Section 13 "Analyzing Search Responses", specifically §13.2 "Grounding of Claims"]**
- **Acknowledged limitation — donated data cannot be publicly released.** Because the traces come from GDPR-compliant data donations from over 600 real users, the authors state that "the donated conversational data cannot be publicly released, we provide mock data to illustrate the data format"; the platform-specific search engines that agents query are also opaque, so some observed behaviour may reflect harness/thrust rather than the underlying model., **[Source: Section 1 "Introduction"; "Limitations"]**

**Takeaway.** Search-calling behaviour is a platform artifact as much as a need signal: the same prompts draw a 14%–83% spread of search-calling decisions, and more searches do not necessarily yield better answers. Attribution is the structural weak point — 14%–53% of claims sit on results the agent fetched but never cited — and users have no visibility into the domain preferences (e.g., Claude never surfacing Reddit/YouTube) encoding these biases.

## Paper 2 — 2508.04604 — TURA: Tool-Augmented Unified Retrieval Agent for AI Search

| Field | Value |
|---|---|
| **arXiv ID** | 2508.04604 (latest version v2) |
| **Title** | TURA: Tool-Augmented Unified Retrieval Agent for AI Search |
| **Authors** | Zhejun Zhao, Yuchen Li, Alley Liu, Yuehu Dong, Xiaolong Wei, Lixue Zheng, Pingsheng Liu, Dongdong Shen, Long Xia, Jiashu Zhao, Dawei Yin (Baidu Inc) |
| **Subject category (arXiv abs page)** | Primary: Computation and Language (cs.CL); cross-listed: Artificial Intelligence (cs.AI); Information Retrieval (cs.IR) |
| **Submission date (arXiv abs page)** | v1 Wed, 6 Aug 2025 16:24:17 UTC; v2 Thu, 12 Mar 2026 12:25:28 UTC — https://arxiv.org/abs/2508.04604 |

**Abstract summary.** TURA is an industrial AI-search architecture from Baidu that combines Retrieval-Augmented Generation with agentic tool use to reach both static web content and dynamic, real-time information such as ticket availability and inventory, which RAG alone cannot access. It is a three-stage framework: an Intent-Aware Retrieval module that decomposes queries and retrieves information sources as Model Context Protocol (MCP) Servers, a DAG-based Task Planner that models task dependencies for optimal parallel execution, and a lightweight Distilled Agent Executor for efficient tool calling. The authors release MCP-Bench, a benchmark from anonymized Baidu production logs with expert annotations, and report the first large-scale industrial validation of a tool-augmented agentic search system serving tens of millions of users since May 2025.

**Findings (extracted from the full text).**

- **TURA unifies static and dynamic sources over a single MCP interface via a three-stage pipeline.** The framework first does LLM-based multi-intent query decomposition into atomic, unambiguous sub-queries; then uses server-level semantic index augmentation (generating diverse synthetic user queries at high temperature to bridge the "lexical gap" between user vernacular and formal API descriptions) and dense vector retrieval (MaxSim over fine-tuned ERNIE embeddings) to retrieve the top-K MCP servers in high recall; then a routerury model classifies query complexity, building a DAG planner for complex tasks that models data dependencies between sub-tasks.; and the Distilled Agent Executor uses mixed-rationale distillation on curated expert trajectories to achieve "comparable fidelity to proprietary LLMs at a fraction of the computational cost and latency" under strict end-to-end latency budgets. **[Source: Section 4 "Methodology", specifically §4.1 "Framework Overview of TURA", §4.2 "Intent-Aware MCP Server Retrieval", §4.3 "DAG-based Task Planner"]**
- **The published architecture is a direct response to a real industrial limitation of RAG: it cannot interact with live services.** The paper states that traditional RAG systems "fundamentally incapable of accessing dynamic, real-time information that is not present on a static webpage but must be generated via interaction," cannot query a flight booking system or e-commerce API, and that this inability "renders them ill-equipped for a significant class of user needs that go beyond static information retrieval." **[Source: Section 1 "Introduction"]**
- **TURA has been in production since May 2025, is the first such architecture validated at that scale, and delivers measurable gains.** Deployed since May 2025 serving tens of millions of users, offline experiments show TURA "substantially improves answer accuracy and faithfulness compared with strong baselines," with ablation studies confirming "the indispensable role of each module," and MCP-Bench — built from anonymized Baidu Search production logs with expert annotations over diverse static–dynamic query scenarios — is released with standardized evaluation protocols. **[Source: Section 1 "Introduction"; Section 2 "Results" (per the framework's claims and published ablation results)]**

**Takeaway.** For practitioners building AI search at scale, the key lesson is that a two-tier "RAG + agent" design is the right shape whenCombining static corpora with dynamic APIs under latency budgets is the hard problem, and TURA shows Beam HTTP-via-MCP with a distilled executor can hit low latency while preserving answer quality. The industrial benchmark they ship is a good template for how to measure whether an agentic search system genuinely beats a dumb retriever rather than just报告 better per-component numbers.

## Paper 3 — 2402.07632 — Understanding the Effects of Miscalibrated AI Confidence on User Trust, Reliance, and Decision Efficacy

| Field | Value |
|---|---|
| **arXiv ID** | 2402.07632 (latest version v4) |
| **Title** | Understanding the Effects of Miscalibrated AI Confidence on User Trust, Reliance, and Decision Efficacy |
| **Authors** | Jingshu Li, Yitian Yang, Renwen Zhang, Q. Vera Liao, Tianqi Song, Zhengtao Xu, Yi-chieh Lee |
| **Subject category (arXiv abs page)** | Primary: Artificial Intelligence (cs.AI); cross-listed: Human-Computer Interaction (cs.HC) |
| **Submission date (arXiv abs page)** | v1 Mon, 12 Feb 2024 13:16:30 UTC; latest version v4 Fri, 26 Sep 2025 07:48:29 UTC — https://arxiv.org/abs/2402.07632 |

**Abstract summary.** Miscalibration of AI confidence -- when stated confidence scores do not match true correctness likelihood -- is pervasive in deployed systems, yet prior work has not tested whether humans can detect it. The authors ran two experiments (N=126 each) on user trust, reliance, and decision efficacy: Experiment 1 found that miscalibrated confidence impairs appropriate reliance and reduces AI-assisted decision-making efficacy, and that users cannot easily detect miscalibration. Experiment 2 examined whether communicating calibration levels mitigates this; it helps users detect miscalibration but decreases trust in uncalibrated AI, leading to high under-reliance and no decision-efficacy gain. The paper ends with design implications and future directions on AI miscalibration risks and ethics.

**Findings (extracted from the full text).**

- **Miscalibrated confidence impairs trust and reliance, and users cannot detect it.** EXP1 (N=126, Prolific, city-image-recognition task, AI accuracy held constant at 70% across training and collaboration phases, three between-subject conditions: underconfident, well-calibrated, overconfident) showed "miscalibrated AI confidence impairs users' appropriate reliance and reduces AI-assisted decision-making efficacy, and AI miscalibration is difficult for users to detect" — participants over-relied on overconfident AI and under-relied on underconfident AI, i.e. most participants did not recognize AI calibration levels well and tended not to detect miscalibration. **[Source: Section 3 "Experiment 1: Users' Awareness of AI Confidence Miscalibration and Effects of Uncalibrated AI Confidence Score", specifically §3.1 "Experimental Design" and §3.1.5 "Experimental Conditions and AI Model"]**
- **Communicating calibration levels helps detect miscalibration but does not improve decision efficacy.** EXP2 (N=126) found that transparently communicating calibration levels helped participants make more sense of miscalibration, but it reduced participants' trust in uncalibrated AI, resulting in high under-reliance on both overconfident and underconfident AI, "it does not improve the decision efficacy" relative to EXP1 — so trust calibration is genuinely hard even when the AI says so. **[Source: Abstract; Section 2 "Related Work"; Section 3 "Experiment 2" (per abstract and design implications)]**
- **Acknowledged limitation — simulated AI and a narrow task.** The study used a simulated AI with manually generated predictions and confidence scores (accuracy held constant at 70%), a city image-recognition task with minimal domain expertise, and a between-subject design limited to the calibration levels tested, so the generalizability of exact effect sizes beyond this controlled setup is an open question for future work. **[Source: Section 3.1.5 "Experimental Conditions and AI Model"; Section 2 "Related Work"]**

**Takeaway.** If you show users "I'm 99% sure," you won't fix under-reliance caused by uncalibrated confidence — in this study, communicating calibration actually made trust in uncalibrated AI worse and efficacy unchanged. The design implication for agentic search: exposure to web search adds a second, unchecked confidence layer; calibration cues alone don't repair it, so disclosure of uncertainty sources (代理人 provenance links) and human-in-the-loop verification need to be part of the default assistant design, not an afterthought.

## Cross-paper takeaways for Thursday

1. **Call volume is not the metric.** Amani et al. show a 14%–83% spread of search-calling decisions on identical prompts, and 15%–20% of claims rest on URLs the agent never cited — so evaluate agentic search on attribution and answer quality, not on how often the model calls a tool.
2. **Safety and calibration compound the problem.** TURA's latency-aware, MCP-based design solves speed; the confidence paper shows that neither more tools nor more transparency fixes miscalibrated trust. Pair any agentic search surface with explicit citation provenance and optional human check before answers hit users.
3. **The gap between industrial and research benchmarks is real.** TURA ships MCP-Bench from anonymized production logs; Amani's dataset cannot be publicly released (only mock data). Worth noting in the sync that we have no clean, shareable eval harness for agentic search right now.
